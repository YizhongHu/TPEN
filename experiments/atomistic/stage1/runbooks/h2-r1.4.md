Status: planning only.  Do not submit from this draft.  The science source is
one released `main` commit that contains #537 (`4f8ebb0f`) and is **dev at or
after the #742 merge commit** (`1c15b144` currently on `dev`); it must include
this reviewed runbook.  The runner records that final main SHA and this file's

bind `--checkout-root` to the exact staged execution checkout.

## Scientific question and fixed analysis

For fixed-nuclei singlet H2 at internuclear distance `R=1.4 bohr` (nuclei at
`[-0.7,0,0]` and `[0.7,0,0]`, including nucleus-nucleus repulsion), what energy
and local-energy variance are obtained by three independently seeded
50,000-update TPEN lineages when each terminal checkpoint is evaluated by four
fresh model-only streams?

The reference is `-1.17447 Ha`, the five-decimal `h2_molecule` value in
`experiments/baselines/systems.yaml`, sourced there to Kolos and Wolniewicz
(1965), as quoted in the PauliNet table.  Its limited precision means this
benchmark may report a signed comparison to the stored value but may not claim
sub-0.01-mHa agreement or superiority.  The planned statistic for each lineage
is the mean of its four stream means at update 50,000, with their spread
reported.  The collector's draw-axis uncertainty assumes retained draws are
independent after the configured burn-in/stride; it does not quantify all
Markov-chain correlation or between-lineage uncertainty.

This run can show only the fixed geometry/model/optimizer/sampler behavior.
It cannot prove exact convergence, transferable molecular performance, a
geometry scan, or a reference-precision claim beyond the five digits stored.
A non-finite row, incomplete grid, wrong identity, or fewer than four streams
is invalid measurement evidence, not a science result.

## Contract, selection rule, and gates

- Train exactly lineages `0,1,2`: three distinct recorded lineage seeds, 4,096
  walkers, 50,000 updates, and one checkpoint at `50000`.
- Select only the terminal checkpoint, mechanically: a lineage is selected iff
  its `status.json` is completed and
  `checkpoints/step_050000/model.pt` exists and is SHA-256 recorded.  No
  energy-based or visually chosen checkpoint is allowed.
- Run streams `0,1,2,3` separately for every selected checkpoint: each is a
  fresh 4,096-walker, 256-draw strict `model_only` restore.  This is 12 eval
  rows and 12,582,912 retained local-energy rows across the experiment.
- Collection must reject any source/config/checkpoint/physical-system identity
  mismatch, non-finite value, incomplete `4096 x 256` grid, non-checkpoint
  provenance, or incomplete/gapped four-stream set.  Preserve all logs,
  manifests, rows, status/config snapshots, records, and collection JSON.
- Abort before submission unless the source is released main, the manager has
  relayed one per-run operator approval for the approved GPU geometry/budget,
  the pending implementation gaps below are closed and independently checked,
  and a current Netscratch quota/access check is satisfactory.  Stop a row on
  an identity or resource mismatch; do not retry, change its shape, or delete
  evidence under this runbook.

the measured A100 seconds/update, `e_h2` the measured GPU-hours per eval
stream, and `m=0.20` the reserve.  The cost is

`GPU-h = (3 * 50,000 * t_h2 / 3600 + 12 * e_h2) * (1 + m)`.

Provisional planning range only: assuming `t_h2=1..5 s/update` and
`e_h2=0.25..1.0 GPU-h`, this is `(41.7..208.3 + 3..12)*1.20 = 53.6..264.4
GPU-h` (nominal `t=3`, `e=0.5`: 157.2 GPU-h).  Run the three lineages in
parallel on three GPUs; training wall time is `50,000*t_h2/3600 = 13.9..69.4 h`
before the selected-checkpoint evaluations.  This fits the 2026-11-29 deadline
only after calibration, approval, queue delay, and the implementation gates are

## Exact command sequence once the blockers close

Set the final source identity once, never edit it in place:

```bash
SOURCE_SHA=<released-main-sha-containing-537-and-742>
CHECKOUT=/scratch/$USER/$SLURM_JOB_ID/checkout
RESULTS_ROOT=/n/netscratch/kozinsky_lab/Lab/rhu/stage1-h2-r1.4/$SOURCE_SHA
PYTHON=/scratch/$USER/$SLURM_JOB_ID/overlay/bin/python
CONFIG_SHA256=$(sha256sum "$CHECKOUT/experiments/atomistic/stage1/configs/h2/train.yaml" | awk '{print $1}')
```

After all three `model.pt` files exist, create `checkpoint-bindings.json` with
one SHA-256 per `(h2,lineage,50000)` key, then run:

```bash
"$PYTHON" "$CHECKOUT/experiments/atomistic/stage1/plan.py" \
  --output "$RESULTS_ROOT/manifest.json" --source-sha "$SOURCE_SHA" \
  --config-sha256 "$CONFIG_SHA256" --results-root "$RESULTS_ROOT" \
  --checkpoints 50000 --lineage-seeds <seed0> <seed1> <seed2> \
  --checkpoint-bindings "$RESULTS_ROOT/checkpoint-bindings.json"
```

For each admitted manifest row, write one row JSON and render it from the final
source, then submit exactly the rendered script only after approval:

```bash
"$PYTHON" "$CHECKOUT/experiments/atomistic/stage1/launch.py" \
  --output "$RESULTS_ROOT/scripts/<row-id>.sbatch" \
  --row "$RESULTS_ROOT/rows/<row-id>.json" \
  --driver experiments/atomistic/stage1/train.py \
  --checkout-root "$CHECKOUT" --python "$PYTHON" --head-sha "$SOURCE_SHA" \
  --results-root "$RESULTS_ROOT" --partition seas_gpu,kozinsky_gpu
```

Use `eval.py` instead of `train.py` for eval rows.  After every required eval
is completed, collect without changing the manifest:

```bash
"$PYTHON" -c 'from experiments.atomistic.stage1.collect import collect; import sys; collect(sys.argv[1], output=sys.argv[2])' \
  "$RESULTS_ROOT/manifest.json" "$RESULTS_ROOT/collection.json"
```

## Current implementation blockers (do not bypass)

1. `plan.py` expands every system and requires checkpoint hashes before it
   emits any train row (`plan.py:22-35`; `protocol.py:526-590`), so it cannot
   make this H2-only train plan before the checkpoints exist.
2. `launch.py` accepts only `test,gpu_test` (`launch.py:20,110-111`) and the
   template requests no GPU, memory, or production walltime
   (`templates/cannon.sbatch:3-7`); it cannot render the approved production
   A100 request.
3. The configs default to CPU (`configs/h2/train.yaml:3`, `eval.yaml:4`), while
   row binding does not bind a GPU/device policy (`launch.py:46-71`).
4. The `config_sha256` is caller-supplied and not defined as a versioned
   multi-file science configuration identity (`plan.py:18-35`).  The exact
   scope and hashing rule must be implemented before release.

The runner records `sbatch` response, job/node/GPU identities, source SHA,
config and record hashes, status/outcome files, manifest hash, collection
output, and an artifact inventory on the run-slice.  Scheduler completion
alone is not a result.
